# Historical travel charges: does changing pricing_rules change existing orders? (read-only review, 2026-10-20)

Owner requirement: **changing current travel pricing must never retroactively change the amount charged on an existing order.** Owner decision: Development's stored configuration ($3.00 per mile beyond a 20-mile radius, free city Detroit) is authoritative; D10's $5.00 is obsolete. Nothing was changed: no migration, no pricing code, no order amount, no `pricing_rules` edit.

## 1. Answer in one paragraph
The amount charged is stored: every one of the 171 Development orders has `travel_fee_cents` (45 above zero, 126 zero), and the calculation basis is stored beside it on all 171 (`travel_per_mile_cents`, `travel_base_radius_miles`, `travel_chargeable_miles`, `travel_total_miles`, `travel_is_flat_fee`, `travel_fee_waived` and its reason). For all 45 orders with a fee, the stored fee equals the stored chargeable miles times the stored rate (45 of 45 within one cent), and every one of them records a rate of 300. Customer-facing displays, the portal and invoices read the stored amount. **The financial preservation requirement is satisfied for every order that has a positive stored travel fee. One latent gap exists for orders whose stored travel fee is zero** (section 4).

## 2. The six questions
1. **Is the finalized fee stored?** Yes, `orders.travel_fee_cents` (integer, never null in Development).
2. **Do screens display the stored fee or recalculate?**
   - New quotes and checkout (`useQuotePricing`, `usePricing`, `Checkout`, `Quote`, edge `complete-booking` / `bookingBuild`) price from the **current** `pricing_rules`; that is correct for a new order, and the result is written to the order (`bookingBuild.ts` lines 287 to 292).
   - Customer portal (`RegularPortalView`, `OrderApprovalView`, `portal-projection`), printed order/invoice documents and the admin order summary (`orderFeeDisplay`, `orderSummaryDisplay`, `buildCurrentOrderSummaryData`) display the **stored** `travel_fee_cents`. `orderFeeDisplay.ts` states the rule explicitly: never show a fee because "today's rule says" so.
   - Invoices copy the order's stored fee into `invoices.travel_fee_cents` when the invoice is created (`orderApprovalService`, `InvoicesList`); they are never recomputed from rules. Two of 82 invoices show 0 although the order now stores 3,659 and 12,159 cents: the order was edited after the invoice snapshot. Amounts paid are not affected; the invoice row is simply older than the order edit.
   - Admin order editing goes through `calculateOrderPricing` (browser) and `staff-order-save` (server, authoritative) and is covered in question 5.
3. **Is a historical snapshot saved?** Yes for per-mile rate, radius, miles, chargeable miles and the flat-fee flag (all 171 rows), and for the waiver flag and reason. **Not saved:** whether the city was "included" (free city) at the time, the zone name (zone overrides), a version or timestamp of the rules used, and any manual-override marker other than the waiver. `pricing_rules.updated_at` is 2025-10-16 although orders show the radius changed during 2026, so edits to `pricing_rules` are not dated.
4. **Can editing `pricing_rules` change an existing order?** Not by itself: no trigger on `pricing_rules` or `orders` and no database function references `pricing_rules` (scheduled pg_cron jobs were not inspected). A stored fee changes only when an admin saves the order and the code decides to recompute (question 5). Today no Development order would change: the 126 zero-fee orders all stay at zero under today's rules (38 have more miles than the 20-mile radius, all in the free city; computed new fees: 0).
5. **Does admin editing preserve or recalculate?** It **preserves** the stored fee only when the address text is unchanged **and the stored fee is greater than zero** (`shouldReuseSavedTravel`, `src/lib/pricing/orderPricingCalculation.ts` lines 205 to 220, mirrored in `supabase/functions/_shared/booking/orderPricingCalculation.ts`; used by `staff-order-save.ts` line 351). Otherwise it **recalculates from today's rules**: a changed address (intentional), a toggled waiver (intentional), or an unchanged address with a stored fee of zero (not intended). Changed values are then written back (`orderChangePlanning.ts` lines 334 to 342).
6. **Can history be reconstructed reliably?** For the charged amount and its inputs, yes from the order row alone (rate, radius, miles, chargeable miles, flat flag, fee). Not for included-city treatment, zone or the rule version. **Do not invent them for older orders.**

## 3. Actual charge versus the formula behind it
- The charge is `travel_fee_cents`. The formula is `round((total miles - radius) x rate)` unless the city is an included city (0), a zone override (flat), or the fee is waived (0 stored; the waived amount is unknown, which the displays report as such).
- Orders in Development: radius 20 on 97 of the 126 zero-fee orders and 17 of the 45 fee orders; radius 15 on 29 zero-fee and 28 fee orders (created July to October 2026). So the radius really was 15 for a period, yet today's Development `pricing_rules` says 20. Because each order stores its own radius, those 57 orders keep their charge regardless of today's value.

## 4. Confirmed latent retroactive-pricing gap (not an observed price change)
**Path:** admin saves an existing order, address text unchanged, stored `travel_fee_cents` = 0 and not waived. `shouldReuseSavedTravel` returns false (it requires a positive fee), so `calculateOrderPricing` prices travel again from the **current** `pricing_rules` using the stored miles. If the radius is later reduced, the rate raised, or the free-city list shortened, such an order gains a travel fee on its next unrelated edit (for example a note or a date change). Where affected: `src/lib/pricing/orderPricingCalculation.ts` (`shouldReuseSavedTravel`, `useSavedTravelFee`), its server twin `supabase/functions/_shared/booking/orderPricingCalculation.ts`, and callers `staff-order-save.ts` and `orderChangePlanning.ts`. Related brittleness: the address comparison is exact text, so a harmless spelling or spacing change counts as "address changed".
**Current exposure in Development:** none today (computed new fees on the 126 zero-fee orders sum to 0). It becomes real the first time rules change in a restrictive direction.
**Why it matters here:** orders with a stored positive fee are protected; free or within-radius orders are not. The owner's rule says no order may change retroactively.

## 5. Minimal compatible remedy (proposal only; no code or schema was changed)
1. **Reuse the stored snapshot whenever one exists**, not only when the fee is positive: in `shouldReuseSavedTravel` (both copies) treat an existing order with an unchanged address and a stored travel snapshot (`travel_per_mile_cents` and `travel_base_radius_miles` not null, and `travel_fee_waived` unchanged) as "reuse", returning the stored fee even when it is 0. Behaviour for positive stored fees, changed addresses, waiver changes and new orders stays identical; existing tests for those paths stay valid and one test per new case is added (stored zero fee, unchanged address, tightened rules: fee stays 0).
2. **Normalize the address comparison** (trim, collapse spaces, case-insensitive) so cosmetic edits do not trigger a re-price. Optional, same function.
3. **Future-order snapshot (only if you want the reconstruction gap closed):** two nullable columns `travel_is_included_city boolean` and `travel_zone text` written by the same place that writes the other snapshot fields. Nullable and unused by existing readers, so backward compatible. Not needed for the charge itself and not required now.
4. **Do not** back-fill historical rates or flags for older orders and do not touch existing order amounts.
Implementation needs your separate go-ahead (it is application code plus an Edge Function redeploy of `staff-order-save`; it belongs with the S6 function stage, not S2).

## 6. What stays unchanged
`pricing_rules` (per mile 300, radius 20, included cities [Detroit]), all order and invoice amounts, D10's historical migration SQL (never to be executed). Read-only queries used: see `sec005-travel-d20-readonly-checks.sql` Q7 to Q9.
