# Step 2: Production/Development compatibility, Step 3 handoff and Step 4 plan

Facts are tagged by provenance: **[PROD-CAP]** the read-only Production catalog capture of 2026-10-16 (Stage B), not refreshed since; **[DEV-LIVE]** read-only Development queries of 2026-10-17; **[LOCAL]** disposable local PostgreSQL rehearsals of the captured schemas; **[REPO]** repository SQL and code. No hosted database was changed and Production was not contacted in this final Step 2 run. A Development finding is never treated as proof of a Production finding.

Canonical plans: Production `production-migration-manifest.csv` (387 rows) with `production-verification-rules.json`; Development `development-migration-manifest.csv` (388 rows), `development-execution-manifest.csv` (259 operations) and `development-verification-rules.json`. Local rehearsals: `evidence/production-plan-rehearsal-results.json` (per-item, 58 steps), `evidence/development-plan-rehearsal-results.json` (21 checks), `evidence/development-execution-test-results.json` (19 checks), `evidence/production-overwrite-check.json`.

## 0. What Step 3 and Step 4 are
- **Step 3 (local, Production-focused security investigation and remediation):** identify the vulnerabilities present in Production, implement the fixes **locally**, test them on local PostgreSQL and commit them locally to `Dev`. No hosted write, no push, no deployment, no hosted role/policy/grant/Storage change.
- **Step 4 (coordinated hosted Development implementation of the Step 2 and Step 3 changes):** apply the committed Step 2 recovery and Step 3 remediation **together** to Development, in the dependency order of section 4. Step 4 must not begin until both workstreams are ready **and the owner authorizes the rollout**. 
- **Production** is never touched by Step 4. A Production rollout is a separate, later decision made only after Development has been validated, with its own approval, restore point, preflight capture and the Production manifest of this repository.

## 1. Compatibility assessment (the ten questions)
1. **Same recovered history for both?** Yes. Both use the same 384 active files, the same recovered SQL and the same three withdrawn originals. The ledgers legitimately differ and must not be forced equal: Production records 277 versions, Development 58; 14 versions are recorded in both; 35 of Production's 58 executables and 8 of its 9 omissions are already recorded in Development; Development's contact-inquiry row `20260814002658` has no Production counterpart (Production will execute the file `20260814120000` under its own version).
2. **Development-specific actions:** history-only/attestation bookkeeping for 225 + 58 versions (259 pre-October operations), the two bucket-limit updates, the exclusion of `update_pricing_rules` and the prohibition on the demo-admin SQL, deny lists, the ledger alias, containment items (14 stubs, schema USAGE, Realtime, pg_net, signup trigger), the `service_role` grants for eight catalog tables.
3. **Production-specific actions:** SQL execution of 58 files (31 older than the latest recorded version `20260928172217`, 22 of the 23 October files), nine history-only omissions, 40 baseline files that are never executed (24 history-only candidates, 16 needing proof), the open question of *how* older-than-latest files are applied (the CLI refuses them without `--include-all`, which is forbidden), a pre-run backup/point-in-time restore point, and owner decisions D-1 to D-7 (e2b2).
4. **Objects that differ** [DEV-LIVE vs PROD-CAP]: 12 tables exist in Development but not yet in Production (created by the pending sequence); `update_pricing_rules` exists only in Production; 31 storage policies in Production versus 6 in Development; buckets `signatures`, `lot-pictures`, `signed-waivers`, `public-assets` are public in Production, private in Development; Production has `public` default privileges and schema USAGE for `anon`/`authenticated`, Development has neither; Development lacks the `auth.users` signup trigger and pg_net; Development publishes only `orders` to Realtime; three Development columns are NOT NULL where Production's are nullable.
5. **Could a recovery migration overwrite a newer definition?** Production: a static scan of the 31 executable files older than Production's latest recorded version found **zero** functions, policies, indexes, constraints or columns that a newer *recorded* migration also names, and the rehearsed sequence changes no function body that a newer recorded migration defines (`production-overwrite-check.json`). Limits: dynamic SQL and unusual `ALTER TABLE` shapes are not scanned; hosted drift since 2026-10-16 is unknown. Development: history-only rows overwrite nothing; re-running the earlier contact-counter files *would* install older function bodies over the current one, which is why they are history-only and re-running is prohibited.
6. **Could ordering regress working Production behaviour?** The rehearsed order ends in the reference catalog (E2G R05) and no financial column of the seven financial tables changed at any of the 58 steps in the synthetic data [LOCAL]. The anonymous surface widens **temporarily** at 13 steps and ends lower (anonymous-executable functions 68 to 6, anonymous-writable tables 55 to 1, [LOCAL] on the restored Production schema); the only incremental *callable* exposure is three portal short-link functions between `20260722211023` and `20261012120000/20261013120000`, with a prepared targeted containment (`evidence/e2h-security-recovery-plan.md`).
7. **Roles, ownership, permissions, RLS, Storage:** both run migrations as non-superuser `postgres`; the ledger is owned by `postgres` in both; RLS is enabled on all application tables in both; Production has `supabase_admin` default ACLs that Development lacks and Production's October file `20261018120000` does not remove them; Storage policy sets differ (item 4) and the October files replace the whole `storage.objects` policy set; bucket exposure differs.
8. **Waits for Step 3:** in Development, every operation whose rule checks a policy, grant or RLS flag must run **before** Step 3 changes those objects (batch class "security-touching"); `service_role` grants, policy restrictions, containment removal and the demo-admin account are Step 3 content; the October block waits for the Step 3 decisions (G2). In Production, no SQL of the 58 waits on Step 3 as such, but October's callers must be confirmed (section 3) and Production's own vulnerabilities (section 2) are remediated by Step 3 before any release.
9. **Needs compatible Edge Functions/application first** [REPO]: waiver functions before `20261014120000`; `customer-portal-*` and `task-evidence` before `20261015120000`/`20261015123000`; `record-site-event` before `20261018120100`; `customer-cancel-order` with or before `20261012120000`; `create-booking`/`complete-booking` with `20261010120000` and `20261017120000`; `staff-order-save` with `20261021120000`; `stripe-refund` with `20261022120000` to `20261024120000`; identify the caller of `get_admin_users` before `20261008120000`; D-2 (nullable surface) before the October booking code.
10. **Step 4 must verify** before and after: see section 4.

## 3. Production risks that matter for the later release
(1) How older-than-latest versions are applied is undecided; (2) a point-in-time restore point must exist before any SQL because a committed file has no ledger-only reversal; (3) the 13 transient anonymous-surface steps and the three portal functions; (4) 16 versions with data or dynamic statements need their preflight counts reviewed; (5) the October financial block needs compatible `stripe-refund`/`staff-order-save`/`complete-booking`; (6) nothing here tests real Stripe, Storage, Supabase Auth or hosted Edge Functions: those are Step 4 and later integration tests.

## 4. Step 4 combined Development rollout: prerequisites and order
0. **Before starting:** the owner has authorized the rollout; Step 2 and Step 3 changes committed and rehearsed locally on both captured schemas; owner decisions answered (`step2-completion.md`, approval package); a Development restore point verified; hosted mechanism designed and approved; Edge Function builds ready.
1. **Read-only validity:** Q00/Q01 (role, ledger = 58 rows), fresh rule evaluation of the next batch.
2. **Bookkeeping part 1** (canary, then batches B02 onward) while the checked objects are still unchanged; every batch is atomic and has a prepared reversal script, which is a documented contingency, not an automatic undo (fresh ledger inspection, dependency check and separate owner authorization first).
3. **Pre-October SQL** (two bucket updates) after the Storage decision.
4. **Deploy compatible backend components** (the deploy-first set above, replacing stubs) before the dependent database changes.
5. **Step 3 database changes** as new reviewed migrations (policy restriction, `service_role` grants, sequence revokes, default-privilege decision), before any broader access is restored.
6. **October block** in version order with the portal-function containment ready and a snapshot before `20261016120000`.
7. **Bookkeeping part 2** for the versions deferred behind October and the storage-policy versions.
8. **Restore broader access last:** remove the schema containment only after the dangerous policies are gone and re-verified.
9. **Verify before and after:** synthetic financial and booking workflows (deposits, balances, refunds, invoices, portal access, Event Essentials), anonymous probes, ledger export comparison, catalog diff against the rehearsed reference, rollback evidence preserved.
