# Hosted Development procedure (design only; nothing here has been run)

Scope: how an **explicitly approved allowlist** (rows of `development-execution-manifest.csv` whose batch the owner has approved in writing) would be applied to the Development ledger. This is a procedure, not a tool: no hosted-capable executor exists or is proposed here, and `scripts/dev/local-executor/` stays loopback-only and unmodified. Production is out of scope. The unit of work is a **batch** (`development-execution-batches.json`), applied by one reviewed script (`build_execution_package.py: batch_script`) with a matching reversal script.

## 1. Mechanism and what is known about it
- Candidate channel: the Supabase integration's SQL call or `psql` with the owner-held credential, both acting as the project's `postgres` role. No Supabase CLI migration/dump/push/repair command is used; no `--include-all`.
- Observed read-only in E2J-B and the final run: a multi-statement call runs in **one implicit transaction** (`SET TRANSACTION READ ONLY; SELECT …` took effect for the SELECT). The scripts therefore contain no `BEGIN`/`COMMIT`, only `SET LOCAL` settings, and rely on a failed assertion aborting the whole call. A destructive rollback proof on the hosted project is deliberately **not** part of the plan (it would itself write); the first hosted write is the single canary row, with its reversal prepared.

## 2. PostgreSQL 17, non-superuser facts (from the 2026-10-16 role/ACL captures; re-verify by Q00/Q30 before use)
`postgres`: not superuser, BYPASSRLS, member of `pg_read_all_data`. It **owns** `supabase_migrations.schema_migrations` (so INSERT/DELETE are allowed) and holds USAGE+CREATE on the schema; it has UPDATE on `storage.buckets` by grant (the table is owned by `supabase_storage_admin`; any trigger on it is unverified and must be read before the SQL batches); `auth.users` SELECT is used by only two rules (`20260302131311`, `20251003170350`; returns booleans). The rules avoid PostgreSQL-18-only catalog behaviour (no `NOT NULL` rows in `pg_constraint`) and use functions present in 17 (`to_regclass`, `aclexplode`, `acldefault`, `has_function_privilege`, `has_table_privilege`). **Local PostgreSQL 18 testing does not prove hosted compatibility**; the first hosted statement for each rule family is the read-only evaluation of the rules (Q-style SELECTs) before any write.

## 3. Allowlist, deny list and identity
Inputs, all hashed in the owner's approval: the batch ids and their versions; `development-execution-manifest.csv` SHA-256; the script template SHA-256 per batch; the filled script SHA-256 (placeholders: `{{BATCH_START_COUNT}}`, `{{APPROVAL_SHA256}}` and, for attestations, `{{ATTESTED_BY}}`, `{{ATTESTED_AT}}`, `{{SCOPE}}`, `{{NOT_PROVEN}}`, `{{EVIDENCE_SHA256}}`). Deny list (never executable, must appear in every allowlist document): Cases 41/42/43, `20260611184401`, `20251003170350` and every October file until its gate. Ledger markers use the prefix `-- BPC-DEV-RECONCILIATION` (kinds: `history-only NOT EXECUTED`, `attestation NOT EXECUTED`, `executed`); the local executor's `-- BPC-LOCAL-EXECUTOR` markers are different, so any future tool must recognise both.

## 4. Per-batch sequence
1. **Validity (read-only):** Q00 (database, role, `transaction_read_only`), Q01 export of the ledger as `(version, name, md5(statements::text))`, saved with its SHA-256; the count must equal the number in the approval. Stop otherwise.
2. **Rules (read-only):** evaluate each operation's rule SQL (`development-verification-rules.json`) as a separate SELECT; every one must return true. For attestation batches also confirm the signed records exist (identity, UTC date, scope, not_proven, evidence hash). Stop on any false.
3. **Fill and verify the script:** substitute placeholders only; compare SHA-256 with the approval; read the script once more for statements other than the ledger INSERT (SQL batches add exactly the migration file verbatim).
4. **Apply:** send the script in one call (`lock_timeout 3 s`, `statement_timeout 60 s`, advisory lock `bpc-dev-reconciliation`, count assertion before and after, per-operation duplicate, predecessor and rule assertions). One batch at a time; never concurrently; never a second batch before step 5 finishes.
5. **Immediate verification (read-only):** Q01 again: count = start + n; the pre-existing rows' md5 are unchanged; each new row exists with the expected marker; rules still true; for SQL batches the bucket row equals the file's values and `statements[2]` hashes to `sha256_lf`.
6. **Log:** append to the protected, hash-chained operator log (previous entry hash, batch id, script hash, Q01 hashes, UTC time, operator). Raw outputs stay outside Git.

## 5. Ordering, duplicate prevention, transactions
Order is the batch order in the CSV: canary, plain history-only by dependency wave, security-touching history-only, attestation groups, then the two SQL batches; predecessors always sit in an earlier batch or earlier in the same batch (asserted in the build and in `developmentExecutionManifest.test.ts`). Duplicates are prevented four ways: the ledger primary key, the per-operation "not recorded" assertion, the advisory lock, and the start/end count assertions. A batch is one transaction: all of it or none of it.

## 6. Restart and partial failure
Because a batch is atomic, a rejected script records nothing: find the cause (the assertion message names the version), fix the cause *outside* the migration (never edit a historical file), tell the owner, then re-run step 1. If the connection drops after sending, **do not resend**: run Q01 and compare with the pre-batch export; if the count and markers show it committed, continue at step 5; if not, the batch did not happen. A batch is never split to "make it pass".

## 7. Recovery
`REVERSAL <batch>` (generated with the batch): deletes exactly this batch's versions **and** only rows whose first statement carries this batch's marker, then asserts the count equals the pre-batch export; for SQL batches it also restores `storage.buckets` to the values read before the batch (both limits were NULL at capture). It requires owner approval, is run only after step 1 for the current state, and is followed by a Q01 comparison with the pre-batch export (all md5 equal). A ledger row can always be removed; schema effects of the SQL batches are reversed only by the recorded previous values.

## 8. Local evidence and its limits
`audit/evidence/tools/test_execution_scripts.py` (19 checks, `development-execution-test-results.json`): scripts run as a non-superuser ledger owner with BYPASSRLS on a scratch restore of the captured Development schema; duplicate, wrong-count and predecessor refusals; whole-batch rollback when one rule becomes false; reversal; SQL batch verbatim with its executed row; no DDL/GRANT in history-only scripts. Not proven: PostgreSQL 17 behaviour, the integration's behaviour on a failing write, Storage triggers, data-rule truth on real data, the signed attestation workflow.

## 9. Immediate stop conditions
Wrong project or role; `transaction_read_only` not as expected for read steps; count differs from the approval; any rule false; script or CSV hash differs; an unrequested statement in the script; unexpected output containing personal or credential data; any need to change a role, grant, policy or setting; an owner instruction to stop.
