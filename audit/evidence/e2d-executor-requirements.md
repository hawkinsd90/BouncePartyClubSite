# E2D requirements for a future migration executor (design only)

**Nothing here was implemented, and no executor was run against any hosted system.** The model executor used in the local tests (`tools/e2d_extra.py`, class `Executor`, local scratch databases only) exists to show that the rules below are testable; it is not the product and must not be pointed at a hosted project. Requirements are numbered so a later stage can trace each to a test. "Evidence" cites what the E2C/E2D local tests showed.

## 1. Why a dedicated executor is needed
- A plain "apply every pending version" tool (the CLI's default, or a push with `--include-all`) would run the 43 baseline/alias files, Case 41 and, for the 58-version plan, the nine omitted versions. E2C showed that running omitted versions late regresses five functions/policies of the finished release (section 4 of `e2c-omission-and-resumption-tests.md`), and that a naive "run what is not in the ledger" resume diverged from the intended final state at 7 of 11 stop points.
- 31 of the 58 candidate versions are older than Production's latest recorded version `20260928172217`; the CLI refuses those without `--include-all`, which is forbidden.
- A static scan of the 58 candidate files (`e2d_extra.py txscan`, `e2d-txscan.json` in the protected scratch folder) found **no top-level BEGIN/COMMIT/ROLLBACK, no non-transactional statement and no CREATE EXTENSION**, so every file can run as one transaction and, if required, in the same transaction as its ledger row.

## 2. Requirements
| ID | Requirement | Evidence or rationale |
|---|---|---|
| X-01 | **Exact allowlist.** The executor takes one approved, immutable document listing every version, file name, SHA-256, kind (`execute` or `history-only`), phase, and for history-only its basis and superseders. It acts on nothing else. The document itself carries a hash that is displayed to and approved by the owner. | E2C manifest (58 execute / 9 conditional); D3 manifest hash `6bc153ae...` pattern |
| X-02 | **Hash check at the moment of use.** Before each file runs, its SHA-256 is recomputed and compared with the allowlist; a mismatch stops the run. | model test: a one-byte change is detected (`hash_mismatch_detected`) |
| X-03 | **Refuse unknown and withdrawn versions.** Any requested or discovered version not on the allowlist is refused; Case 41 `20260305203528`, Case 42 `20260407203226` and Case 43 `20260407211122` are named in a deny list and can never be recorded or run. | model test: all three withdrawn versions and an unknown version refused |
| X-04 | **Never "run all pending".** The executor never derives its work from the repository directory or from "pending" in the history table. Its work list is allowlist minus ledger. | E2C naive resume diverged at 7 of 11 stops |
| X-05 | **Order independent of "latest recorded".** Versions older than the latest recorded version run normally, in allowlist order; the executor does not use the CLI's ordering rule and never calls `--include-all`. | 31 of 58 are older |
| X-06 | **One transaction per file, ledger row in the same transaction when possible.** Because the 58 files contain no transaction control, `BEGIN; <file>; INSERT ledger row; COMMIT` is feasible and removes the crash gap between "applied" and "recorded". If a later file does contain transaction control, the executor stops and requires a documented exception. | txscan; atomicity test (4 of 4 failing files left no partial change) |
| X-07 | **Distinct ledger kinds.** A successfully executed version is recorded with a marker that includes the allowlist hash and the executor run id. A history-only version is recorded with a different marker that states "NOT EXECUTED", the basis and, for a qualified attestation, who attested, when and what was not proven. The marker is stored where the evidence can be queried without parsing free text (a companion audit table is preferable to relying on the `statements` array alone). | local ledger: 58 `executed` and 9 `history-only` rows distinguishable by a single query |
| X-08 | **History-only is never evidence of execution.** Reports, dashboards and the pending-set calculator must show the two kinds separately; a history-only row must not be counted as "applied". | owner decision D-6 |
| X-09 | **Truthful timing of history-only records.** A history-only record for a superseded version is written only after the version that makes it true has succeeded (check against the ledger). The net-zero pair and `20261010110000` may be recorded first only after a catalog precondition holds (policy absent; column present). A record whose precondition fails is not written and the run stops. | model test: no premature "superseded by" record at any of 18 interrupted runs |
| X-10 | **Pre-phase preconditions.** Each phase starts only if its preconditions pass and are logged: fresh capture inside the freshness window; history equals the expected pre-state (277 recorded versions, latest `20260928172217`); the read-only data preflight results are present and within limits; Edge Function and security prerequisites confirmed by the owner for that phase; backup/restore point confirmed. | E1 preflight set; E2B-2 sequence outline |
| X-11 | **Stop on any unexpected result.** Any error, hash mismatch, precondition failure, unexpected row count or unrecorded in-flight state stops the run immediately. The executor never skips a failing version to reach later ones and never marks a failed version. | D4 B1 to B5: failures stop at the intended migration with the failing version not in the ledger |
| X-12 | **Safe interruption and resumption.** Resumption recomputes everything from the ledger and the allowlist (stateless); it must not trust a progress file. An in-flight marker written before each file and cleared after the ledger row detects a crash inside the gap; a version found in flight is not re-run automatically unless its re-application class (`d4-reapplication-matrix.csv`, `e2d-scenario-comparison.csv` D4-C) is "idempotent", otherwise a human verifies the catalog first. | E2C proper resume reached the intended final state at 11 of 11 stops |
| X-13 | **Ordering safety for the release.** Phase boundaries are explicit; the executor refuses to pause between the Development-line migrations and the October lockdown (`20261013120000`) unless the owner records a decision, because the anonymous function surface is widest there in both sequences. | `e2d-security-intermediate-states.md` section 4 |
| X-14 | **Deployment ordering gates.** `20260722172048` must run before the booking function that sends a NULL surface is deployed; `customer-cancel-order` with or before `20261012120000`; signed-URL consumers before `20261014120000`/`20261015120000`. The executor does not deploy; it requires the owner's confirmation of each gate before the phase that depends on it. | D-2; D3 findings F-4 |
| X-15 | **Dry run produces the plan, not effects.** A dry-run mode prints the ordered list (version, hash, kind, phase) and diffs it against the allowlist; it must show exactly 58 execute and 9 history-only (or whatever the owner approved) and zero other versions. | E2C manifest |
| X-16 | **Audit evidence.** Every action writes an append-only record outside the target database as well: run id, allowlist hash, version, kind, start/end time, outcome, error text, ledger row id, post-step fingerprint of the affected catalog categories. Failures and refusals are recorded the same way. | local runs produced per-step fingerprints (`e2c-steps.json`, `e2d-security.json`) |
| X-17 | **Post-run verification.** After the last version, the executor runs the catalog assertions (the 37 D3 checks and the 19-category comparison against the approved reference), compares the ledger with the allowlist (58 executed, 9 history-only, none else) and fails the run if either differs. | D3, E2D |
| X-18 | **No credentials in logs; least privilege.** The executor uses a dedicated, time-limited role approved for the run; no password, token or connection string is written to any log or evidence file. | standing rule |
| X-19 | **Environment guard.** The executor knows which project it is allowed to touch (project reference from the approved document) and refuses any other; it has a distinct "local scratch only" mode used by rehearsals. | Development and Production are separate runs with separate allowlists (D-7) |
| X-20 | **Rehearse before use.** The executor itself must pass the E2C/E2D test matrix on a scratch restore of the Production snapshot (full run, interrupt at every superseder boundary, failure fixtures, hash tamper, withdrawn/unknown refusal) before any hosted use, and the rehearsal result is attached to the approval. | this stage's model tests |

## 3. Allowlist document (shape only; no executable content)
```
{ "environment": "<project ref>", "created": "<utc>", "base_history": {"count": 277, "latest": "20260928172217"},
  "items": [ {"order": 1, "version": "...", "file": "...", "sha256": "...", "kind": "execute", "phase": "P3", "requires": ["..."]},
             {"order": 2, "version": "...", "file": "...", "sha256": "...", "kind": "history-only", "basis": "superseded by <versions>", "record_after": ["<versions>"]} ],
  "deny": ["20260305203528", "20260407203226", "20260407211122"], "document_sha256": "..." }
```

## 4. Out of scope here
Choosing the implementation language or tool, writing it, deciding the owner approvals, and any hosted use.
