# E2G security analysis: failure and recovery in the critical migration window

Local scratch PostgreSQL only; synthetic data; no hosted system. No existing migration, in particular none of the October security migrations, was changed. Measurements: `e2g-executor-test-results.json` (`window_measurements`, tests W00 to W4b) and the E2D per-step probes (`e2d-security.json`, protected scratch folder).

## 1. What "broader than intended" means here
Start state (restored Production schema): **68** `public` functions executable by `anon` and **55** `public` tables on which `anon` has INSERT, UPDATE or DELETE (all with row-level security). Finished state of the 58-version release: **6** functions and **1** table. A stop is "broader" when either count exceeds the start state. From E2D, the 40 stop points `20260716151458` to `20261011120000` are broader; the start state and every stop from `20261012120000` onward are not. New functions are executable by `anon` through the default function privileges until the lockdown migrations run; no table with anonymous write privilege ever had RLS disabled in any measured state.

## 2. Measured failures
| Scenario | Failure | Anonymous surface at the failure point | Broader than start? | Anonymous insert into `invoice_links` |
|---|---|---|---|---|
| W3 invalid order item | `20260716151458` (first window migration; its transaction rolled back) | 68 functions / 55 tables = the start state | no | rejected |
| W4 lock held on `orders` | `20260925151621` (lock timeout) | 79 functions / 64 tables (state after `20260820165646`, from the E2D probes) | **yes (+11 / +9)** | rejected |
| W1 duplicate active portal link | `20261009120000` | **69 / 65** (measured on the failed database) | **yes (+1 / +10)** | rejected |
| W2 role outside the vocabulary | `20261016120000` (after the lockdown migrations) | 6 / 2 | no (narrower than start) | rejected |
The anonymous INSERT into `invoice_links` was rejected at every failure point, as expected: the 58-version path never creates the temporary policy of the omitted pair (the pair is recorded history-only before the first execution and is never selectable).

## 3. Can the executor recover without leaving a broader state?
- **Fixable cause: yes.** In W1, W2, W3 and W4 the executor stopped, the failed version was not recorded, and after the cause was removed (a data fix, or the lock released) a plain resume completed and returned the database to the intended final state: catalog fingerprint equal to the LF reference and the final surface of 6 functions / 1 table (W2f, W3f, W4b; W1e completed 58/9). Recovery therefore depends on how fast the cause can be fixed, not on the executor.
- **Unfixable or slow cause: the executor cannot narrow the surface.** It never runs compensating SQL. During the time between a failure and a resume the database is in the measured state above (up to +11 functions and +10 tables over the start).
- **Candidate containment (scratch-only SQL, not part of the executor).** In W1 a reviewed-style script revoked `anon` access on every function and table that was not anon-accessible at the start. It brought the surface from 69/65 to **54/54**, below the start state, because the two lockdown-type migrations that had already run (`20261007120000`, `20261008120000`) had removed anonymous access from some start-state functions and the new window functions were revoked. **Limits found:** (a) revoking from `PUBLIC`, which is what removes anonymous access to functions granted that way, also removes access for other roles that relied on the `PUBLIC` grant; (b) after containment and a resume, **2 functions had different privileges from an uncontained run** (`check_product_availability(jsonb,date,date,uuid)` and `get_public_nav_menu_groups()`), because their creating migrations had already run and a resume does not re-run them; the final catalog differed from the reference in the `functions` category. A containment script therefore needs per-function review and a matching re-grant step; it cannot be a generic revoke.

## 4. Unresolved prerequisites (not silently fixed)
1. **A pre-agreed recovery action for a failure inside the window** (owner decision U-E2E-5): resume quickly; or a reviewed containment script **with its re-grant counterpart** (a hosted write needing its own approval); or restore from backup/point in time. None is implemented or authorized.
2. **Preventing the known causes.** The three data causes tested (duplicate active portal link, role outside the vocabulary, order item without exactly one reference) correspond to checks in the prepared Production preflight set (`e1-production-preflight-queries.sql`, 24 checks, never run against any hosted database). Running that set before the window removes the most likely reasons for a failure.
3. **Lock behavior under real traffic.** The test showed that the executor fails fast on a held lock (`lock_timeout`), leaving the wide state until a retry; on a busy hosted database retries and a quiet window need a plan (U-E2E-13). Concurrent application traffic was not simulated.
4. **Deployment coordination.** Edge Functions that depend on the lockdown (`customer-cancel-order` with or before `20261012120000`) and signed-URL consumers (before `20261014120000`/`20261015120000`) must be ready before the window starts, otherwise a resume after a long pause meets a changed API surface.
5. **Hosted privileges and runtime.** Local runs used a superuser and stubbed platform schemas; whether the hosted `postgres` role can perform the storage, `auth.users` trigger and default-privilege statements is unverified (U-E2E-12).
6. **Platform default privileges** (`supabase_admin`) remain permissive after the release (finding F-2) and are a Step 3 matter.
7. **No change to migrations.** If safe recovery were to need a SQL change inside the migrations (for example granting the new functions to `authenticated` only from the start), it would be a new, reviewed migration decision; E2G made none.

## 5. Conclusion
The executor makes a failed attempt **safe from double application, partial application and accidental execution of omitted or withdrawn migrations**, and a fixed-cause resume restores the intended final state. It does **not** by itself keep the anonymous surface no broader than the start while the cause of a failure inside the window persists. That residual risk is bounded by the 40-stop critical window, is independent of the shortened sequence (the 67-version path has the same window plus the open-policy exposure), and needs the prerequisites above before any hosted use.
